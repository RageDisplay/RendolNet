# WireGuard

WireGuard-туннель задаётся как интерфейс в общем документе конфигурации. У него
есть адреса, MTU, роль и зона, поэтому к расшифрованному трафику применяются те
же правила между зонами, NAT, маршруты и откат конфигурации, что к физическим
портам. Агент использует ядерный WireGuard через `wgctrl`; userspace-демон и
утилита `wg` на узле не нужны.

## Удалённый клиент

1. Откройте «Сеть» → «WireGuard» и создайте туннель. Укажите свободную сеть,
   например адрес узла `10.200.0.1/24`, UDP-порт `51820`, MTU `1420` и зону.
   Приватный ключ сервера генерируется автоматически.
2. Примените конфигурацию. Разрешите входящий UDP-порт туннеля правилом из
   внешней зоны в `self`: это правило пропускает ещё зашифрованные пакеты на
   физическом WAN-интерфейсе.
3. Нажмите значок скачивания у туннеля, выберите «Новый клиент», задайте его
   имя и свободный адрес, например `10.200.0.2/32`. Укажите внешний DNS-имя или
   IP узла и UDP-порт в endpoint.
4. В `AllowedIPs` клиентского файла перечислите сети, которые нужно отправлять
   через туннель. Значение `0.0.0.0/0, ::/0` заворачивает весь клиентский
   трафик. Скачайте `.conf` и импортируйте его в клиент WireGuard.
5. Ещё раз примените конфигурацию узла: только после этого активируется новый
   публичный ключ peer. Для доступа клиента к другим зонам добавьте правила из
   зоны туннеля. Для выхода в интернет нужен маскарад или SNAT через WAN.

При создании клиентского конфига узел получает только публичный ключ peer.
Приватный ключ существует в скачанном файле и в состоянии диалога, но не пишется
в конфигурацию или базу. Повторно скачать тот же файл нельзя: перевыпуск заменяет
публичный ключ peer, и старый клиент перестаёт подключаться после применения
конфигурации. Перед выдачей файла нужно применить накопленные изменения, чтобы
публичный ключ сервера в файле соответствовал работающему туннелю.

Приватный ключ сервера сохраняется в `interfaces[].wireguard.private_key`, чтобы
агент мог восстановить туннель после перезапуска. Он также попадает в экспорт и
ревизии конфигурации, поэтому доступ к ним нужно ограничивать как к секретам.

## Site-to-site

Для каждой стороны добавьте peer с публичным ключом другой стороны. В
`AllowedIPs` укажите адрес peer внутри туннеля и удалённые сети, которые эта
сторона должна отправлять ему. На обеих сторонах добавьте статические маршруты к
удалённым сетям через WireGuard-интерфейс: `AllowedIPs` не создаёт маршруты в
таблице Linux автоматически.

`AllowedIPs` одновременно разрешает источники расшифрованных пакетов и выбирает
peer для исходящих. Поэтому сети разных peers одного туннеля не должны
пересекаться. Endpoint можно не задавать у стороны, которая только принимает
подключения. Для инициирующей стороны за NAT обычно задают
`persistent_keepalive: 25`.

## Пример в конфигурации

```json
{
  "name": "wg0",
  "role": "lan",
  "zone": "vpn",
  "enabled": true,
  "addresses": ["10.200.0.1/24"],
  "mtu": 1420,
  "wireguard": {
    "listen_port": 51820,
    "private_key": "base64-encoded-private-key",
    "peers": [
      {
        "name": "laptop",
        "public_key": "base64-encoded-public-key",
        "allowed_ips": ["10.200.0.2/32"],
        "persistent_keepalive": 25
      }
    ]
  }
}
```

Зона `vpn` должна быть создана в разделе «Интерфейсы». Дополнительно можно задать
`preshared_key` и `endpoint`. Ключи имеют стандартное base64-представление
WireGuard длиной 32 байта после декодирования.

WireGuard несовместим с DHCP, VLAN, DHCP-сервером и ролью `mgmt`. Агент удаляет
только исчезнувшие из конфигурации туннели со своей меткой `rendolnet`; чужие
WireGuard-интерфейсы не затрагиваются.

## Состояние

На странице показываются последний handshake и суммарные RX/TX peers. Отсутствие
handshake обычно означает, что внешний UDP-порт закрыт, endpoint неверен, ключи
не совпадают или клиент ещё не отправлял трафик. WireGuard не поддерживает
подключение по TCP.

HTTP API:

- `GET /v1/wireguard` — устройства, публичные ключи, peers, handshake и счётчики;
- `POST /v1/wireguard/keypair` — новая пара ключей, доступно operator и admin.
